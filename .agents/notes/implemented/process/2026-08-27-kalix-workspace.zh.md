# Agent Note: Kalix workspace

Status: implemented

[English](2026-08-27-kalix-workspace.md) | 中文

## 问题

Kalix Code 需要一个可长期维护的位置来保存产品方向和功能立项信息，同时不能在既有插件单体仓库之外再建立第二套源码层级。将规划混入各软件包文档会模糊源码归属，而未被记录的功能工作会使后续评审和交付缺乏一致性。

## 决定

仓库在根目录的 `.kalix/` 中保存 Kalix 层级的产品规划。`ROADMAP.md` 按成果安排工作，`FEATURE_BRIEF.md` 定义有实质功能的立项问题，`DECISIONS.md` 记录当前仓库层级的选择和暂缓的问题。该目录不拥有运行时代码、应用、生成文件、软件包接口或构建产物。

既有单体仓库层级仍然是源码归属模型。新的实现工作继续放在相应的既有软件包、应用、示例、脚本、文档、Python、原生代码或供应商位置。普通功能工作保留继承的 `dsh` 软件包、命令、导入、配置和数据词汇。Kalix Code 是仓库层级的产品身份；完整的技术重命名是一个单独的、覆盖整个仓库的决定。

`.env.example` 说明真实 API 测试和演示所使用的可选本地变量。它不包含凭据值，并将 `.env` 保留为本地秘密信息的位置。

## 考虑过的替代方案

**建立并行的 `kalix/` 源码树** 会重复软件包归属，并分裂构建、测试和文档责任。既有工作区已经提供了合适的源码位置。

**将规划材料加入根 `README.md`** 会让项目入门文档承载易变的产品管理细节，也会为内部工作流变化扩大已配对的公开文档范围。

**在准备期间重命名软件包和命令** 会产生混合的技术词汇，而清单、导入、配置、生成引用、测试、夹具、文档和发布元数据所需的协同改动尚未完成。

## 后果

维护者拥有一个可发现的位置来保存 Kalix 专属规划，功能提案也从一套一致的设计和验证问题开始。在未来的发行、提供商、兼容性和发布决定保持明确的同时，仓库仍与继承的技术词汇保持构建兼容。

该工作区新增了一个规模较小且需要维护的文档区域。对其方向或源码归属的实质性修改仍须遵循仓库现有的文档、测试和 Agent Note 实践。
